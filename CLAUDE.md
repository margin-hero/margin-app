# Margin Hero (margin-app)

Multi-tenant SaaS margin/profit calculator for UK e-commerce sellers. Main competitor is Sellerboard. Core focus is strictly **margin**. Don't broaden scope into unrelated features.

I'm building this myself ("vibe coding") and I'm not a professional developer. Explain what you're changing and why in plain English. Keep changes small and focused, and ask before large refactors.

## Stack
- Next.js 16.3 (App Router), React 19.2, TypeScript, Tailwind v4
- Supabase (Postgres) via `@supabase/supabase-js`
- Hosted on Vercel, repo at github.com/margin-hero/margin-app, domain marginhero.co.uk

In every new-table migration:
  - Add that `tenant_id` column and policy, `enable row level security`, and `grant select, insert, update, delete ... to authenticated` (never `anon`). No allow-all policies.

  - The SQL editor isn't logged in, so hand-written inserts there must give `tenant_id` explicitly.
  - The service-role key bypasses RLS: server-side only, never in client code.

## Money & margin rules (important, these bugs have happened before)
- All money is stored and calculated in **integer pence** (`*_pence` columns). Watch for fractional-penny rounding in VAT splits.
- **Aggregation:** sum totals first, THEN derive percentages from the totals. Never average per-order percentages.
- `margin_percent` uses **net revenue** as the denominator.
- **Gross Profit** = revenue minus landed product cost only (`product_cost_pence` = every `cost_types` row with `in_gross`: all-in landed cost, or product cost + inbound freight + import duty).
- **Net Profit** = revenue minus everything: product cost, other costs, fees, shipping (`total_cost_pence`).
- **Net after overheads** = Net Profit minus each sale's share of overheads. Overheads are NOT in `order_margins`: they're shared at reporting time for the page's date range by `lib/overheads.ts` (`allocateOverheads`), never touching Gross.
- Two VAT modes: VAT registered (net figures throughout) vs not registered (VAT is an irrecoverable cost). VAT rate is per product, not flat. `tax_regime_id` exists for future international taxes.
- Landed cost from third-country imports and in-house picking/packing carry **0% VAT**, not the 20% default.
- COGS must scale by quantity. Bundles use `units_per_sale` on `platform_listings` → `effective_qty`, used for both COGS and shipping lookup.

## Date-tracked costs
- `cogs_components` and `shipping_rules` both use `effective_from`. The view picks the rate where `effective_from <= order_date`.
- UI distinction: **Edit** = correct a mistake (retroactive). **Add** = genuine cost change over time (preserves history).
- New costs for historical products must be backdated or they won't apply to past orders.

## Key tables / views
- `tenants`, `master_products`, `platform_listings`
- `stores`: one shop on one platform (e.g. two TikTok shops for different brands). VAT registration is dated: `store_vat_status` (store_id, vat_registered, effective_from; each store gets a 2000-01-01 starting row by trigger) and the views use the status on each order's date (refunds: the original sale's date). `stores.vat_registered` = the status today, kept in step by a trigger (used by overheads and lists; never update it directly, add / edit `store_vat_status` rows on `/stores`). Not `tenants.vat_registered` (that's business-wide overheads only). `platform_listings.store_id` is required; a trigger copies `platform_id` from the store. Importers pick a store via `components/StorePicker.tsx` and call `importOrdersForStore`. `shipping_rules.store_id` is optional (null = all stores; a store-specific rule wins). `tiktok_sku_catalog` is per store.
- `platforms`: shared across tenants, added by migration only (no UI, to avoid duplicates). `integration_type` (e.g. `'mirakl'`) is how importers find their platforms; `'csv'` = no dedicated importer, orders come in via `/upload` (Argos is on Mirakl; eBay has `'ebay'`, Temu `'temu'`)
- `order_line_items`: unique on `(platform_listing_id, external_id)` for dedupe on re-uploads
- `cogs_components`, `shipping_rules`
- `order_line_fees`: each order line's fees split by type (`fee_types`: fixed list, migration-only; codes mirrored in `lib/fees.ts`), with `source_label` = the fee's name in the channel's file. Importers pass `NormalizedOrder.feeBreakdown`; `importEngine` saves it and tops it up with an `unspecified` row so it always adds up to the line's `fees_gross_pence` / `fees_vat_pence` (which `order_margins` still reads). Not yet shown on any page. TikTok only splits out affiliate / seller-funded promotion so far (TikTok's own fee columns still to map).
- Shipping profiles: `courier_services` (+ dated `courier_service_prices`, per parcel, with the service's VAT rate) → `shipping_profiles` with `shipping_profile_bands` (qty range → N parcels × a courier service; `max_qty` null = "and above"; bands are NOT dated) → `product_shipping_profiles` (store_id null = all stores; a store override with null profile = deliberately no shipping cost). Shipping priority in `order_margins`: label cost → `shipping_rules` (exact qty) → profile → missing. `order_margins.shipping_source` = 'label' | 'rule' | 'profile' | 'none' | 'missing'. Pages: `/couriers`, `/shipping-profiles`, assignment on `/products/[id]`.
- `cost_types`: fixed list (migration-only) that `cogs_components.component_type` must reference. `basis` = `per_unit` (× effective_qty) or `per_order` (once per order line; there's no order grouping yet, so a multi-product order is charged per line). `in_gross` = landed cost. `cogs_components.description` is optional; "latest cost wins" applies per (type, description). Per-order costs appear in `other_cost_pence` and separately as `per_order_cost_pence`.
- `overheads`: recurring (weekly / four_weekly / monthly / quarterly / yearly, start + optional end date) or one_off (spread over `spread_months`). `store_id` null = whole business (VAT treatment from `tenants.vat_registered`), set = that store only (store's VAT). Converted to a cost per day, shared by `tenants.overhead_allocation_basis` ('revenue' default | 'units' | 'orders'). "Change amount" ends the old row the day before and inserts a new one (history kept). Shown on `/overheads`, `/channel-overview` (per store + totals) and `/margins?overheads=1`.
- `channel_sku_ids` (was `tiktok_sku_catalog`, renamed 2026-10-06): maps a channel's own numeric SKU IDs → your seller SKUs, per store, for channels whose reports don't show your SKU: TikTok and Temu (`SKU_ID_CHANNELS` in `lib/stores.ts`; `usesSkuIds(store)` / `skuIdChannel(store)` by platform name; `isTikTokStore()` only for TikTok-specific bits). Edited in `components/StoreListings.tsx` (on `/mappings` and `/products/[id]`; the ID is required on every listing in those stores; one ID can only belong to one store SKU), bulk via `components/TikTokCatalogUpload.tsx` (TikTok only so far) and the optional `channel_sku_id` column in `/catalog-import` (old `tiktok_sku_id` still read). Importers translate the ID to the seller SKU before `importOrdersForStore`; unknown IDs fall back to the raw ID so they're held back. `/tiktok-catalog` just redirects to `/mappings`.
- `order_margins` (view): revenue_pence, product_cost_pence, total_cost_pence, margin_pence, margin_percent, price_per_unit_pence, etc. Sales only.
- `order_refunds`: one row per refunded order line (Amazon so far), matched by SKU (`platform_listing_id`) and linked to its sale by `original_external_id` = the sale's `external_id` (no FK: the sale may be imported later). Amounts positive = given back; `fees_gross_pence` = the change in fees as a cost (negative when fees are returned). `return_shipping_cost_pence` = return label. Imported via `importOrdersForStore(..., { refunds })` (`NormalizedRefund`). Items are assumed resaleable (product cost comes back).
- `margin_lines` (view): `order_margins` sales + one NEGATIVE row per refund (on its refund date), same columns plus `line_type` ('sale' | 'refund'), `refunded_units`, `gross_sales_pence`. Dashboards (Channel Overview, Margins / Opportunities via `skuStoreMargins`, SKU Detail, Trends, /order-lines) read this, so totals are net of refunds. Count orders / units sold / AOV from `line_type = 'sale'` rows only; refund rate = refunded units ÷ units sold. `allocateOverheads` gives refund rows no share. /costs, the missing-costs banner, /overheads and /products/[id] stay on `order_margins`. Refunded units: the row's `qty`, else refunded gross ÷ the sale's price per unit (rounded, capped at units sold; 1 if the sale isn't imported).
- `sku_channel_margins` (view): per SKU x channel margins. No longer used by any page (`/margins` reads `order_margins` and aggregates itself)
- The current tenant comes from the login: RLS only returns the logged-in user's own `tenants` row, so read it with `.from('tenants').select(...).single()` (no name filter). For an update/delete filter, use `supabase.rpc('current_tenant_id')`. New rows get `tenant_id` by default. Never look a tenant up by name.

## Code structure
- `lib/supabase.ts`: shared Supabase client (browser, `@supabase/ssr`, session in a cookie). Server pages (`/margins`, `/opportunities`, `/order-lines`) must use `createServerSupabase()` from `lib/supabaseServer.ts` and pass it to shared helpers (`loadMarginRanges(db)`, `loadStores(db)`, `loadSkuStoreMargins(..., db)`, `loadOverheadSetup(db)`), or RLS will treat them as logged out.
- Login: `proxy.ts` (Next 16's name for middleware) sends logged-out visitors to `/login`, except `OPEN_PATHS` (keep in step with `PUBLIC_PAGES` in `AppShell.tsx`) and `/api/*`. No sign-up page: users are created in Supabase and linked in `tenant_members`; `current_tenant_id()` (SQL) returns the logged-in user's tenant.
- `lib/importEngine.ts`: shared SKU-matching / dedupe / insert logic. All platform importers must reuse this, not duplicate it (including `/upload`, the generic CSV importer).
- **Set-up flow** (keep it linear): `/getting-started` checklist (ticks from data: stores → couriers → shipping profiles → products with store SKUs → landed costs → sales → overheads optional); each set-up page ends with `components/NextStep.tsx`. `/products` has "Add product" (then opens `/products/[id]?new=1`); `/products/[id]` is the product's home, in numbered sections with a progress strip: 1 Details (SKU, name, sale VAT rate, delete if no store SKUs), 2 Store SKUs, 3 Costs, 4 Shipping. `components/StoreListings.tsx` = one product's store SKUs editor (add / edit / move / delete + TikTok SKU IDs), shared by `/products/[id]` and `/mappings` ("Store SKUs": every product at once; products are no longer created there).
- `components/Nav.tsx`: collapsible left sidebar (Dashboards / Import / Manage groups; Manage has Getting started, then Products / Shipping / Costs subheadings). Rendered for every page by `components/AppShell.tsx` in `app/layout.tsx` (skipped on the public homepage `/`), so pages must NOT include `<Nav />` themselves. Add new pages to `NAV_GROUPS` with a `lucide-react` icon.
- `NormalizedOrder.saleVatPence` / `shippingRevenueVatPence` may be `null` when a channel doesn't report sale VAT: `importEngine` then works it out from the product's `vat_rate` (gross × rate ÷ (1 + rate)).
- `importEngine` holds back orders whose SKU isn't mapped in the store (listed via `describeImportResult`) unless `createUnknownSkus` is set (tick-box `components/CreateProductsToggle.tsx` on each import page). A store SKU that exactly matches a product's `standard_sku` is still linked automatically.
- `/catalog-import`: bulk products + store mappings from CSV/XLSX (one row per listing). The `store` column is the store name, or "Name (Platform)" when the name is used on more than one platform (store names are unique per tenant + platform, not per tenant). Only adds, never changes or deletes; clashes are reported as problems.
- `/cost-import`: bulk costs from CSV/XLSX (one row per cost; cost_type by label or code; vat_rate and effective_from required, no defaults). Adds only: a different amount for the same product/type/description/date is reported, never overwritten.
- `/costs` ("Cost Check" in the menu): overview of every product's current costs, with a one-click "Backdate cost to <date>"; flags products whose orders have £0 product cost (missing or not-backdated costs) and `shipping_source = 'missing'`. `components/MissingCostsBanner.tsx` shows the same warning above dashboards (via AppShell).
- `lib/readSpreadsheet.ts`: shared CSV/XLSX reader (Papa for CSV to keep exact text, SheetJS for Excel with date-cell conversion). Use it for new file importers.
- `lib/skuStoreMargins.ts`: all-time net margin per product × store plus which products are listed where (from `platform_listings`). Shared by `/margins` and `/opportunities`. Only stores with at least one listing or sale are included.
- `lib/fetchAll.ts`: Supabase silently caps results at 1,000 rows. Any query that can return more (orders, listings, products, catalogs) must go through `fetchAll` with an `.order()` on a unique column + `.range(from, to)`.
- `lib/theme.ts`: shared brand palette + fonts (from the homepage). Use these instead of hardcoding colours.
- Pages: `/margins` (SKU x store matrix, the styling template: period pills + custom dates, each cell = margin % over net profit £ per unit or total, or "Not listed"; sortable by any column's % or £; `/grid` redirects here), `/opportunities` (profitable products not listed in every store), `/order-lines` (unlisted: every order line's cost breakdown, for checking calculations), `/channel-overview`, `/sku-detail`, `/trends`, `/upload`, `/amazon-import`, `/tiktok-import`, `/mirakl-import`, `/onbuy-import`, `/shopify-import`, `/ebay-import`, `/temu-import`, `/stores`, `/catalog-import`, `/costs`, `/cost-import`, `/couriers`, `/shipping-profiles`, `/overheads`, `/settings`, `/mappings` (Store SKUs), `/products`, `/products/[id]`, `/getting-started`

## Platform import notes
- **Amazon settlement:** multi-row per order; group by order-item-code, revenue = Principal + Tax, costs = ItemFees, use "Shipping label purchase" if present else `shipping_rules`. **Refunds** (`transaction-type` = Refund): grouped by adjustment-id + order-item-code (= `externalId`; order-item-code links to the sale); Principal/Tax negative = refunded; ItemFees positive = fees returned (Commission, DigitalServicesFee), negative = charged (RefundCommission); `quantity-purchased` is blank. "Shipping label purchase for return" (other-transaction, order-id only) = return postage, matched to that order's refunds in the same file. SAFE-T reimbursements not yet handled.
- **TikTok settlement:** statement (.xlsx, possibly several tabs, or CSV); the tab is found by its "Order/adjustment ID" column (`readSpreadsheet` `sheetWithColumn`). One "Order" row per line item; `externalId` = `${Order/adjustment ID}_${SKU ID}`. IDs are 19 digits: never read them as numbers (`readSpreadsheet` throws on unsafe integers in Excel; Papa keeps CSV text; non-digit IDs like 1.72964E+18 are skipped with an "opened in Excel" warning). SKU ID → seller SKU via `channel_sku_ids`. Revenue = "Net sales" (net of seller discounts and same-row refunds); rows with Net sales <= 0 skipped. "VAT" 0 for UK sellers → `saleVatPence: null`. Fees = "Fees" total, split by `FEE_COLUMNS` (commission fee → commission, Shipping service fee → shipping, Managed service plan → other_fee, campaign / Smart Promotion / GMV Max → advertising, affiliate columns → affiliate, Co-funded promotion (seller-funded) → advertising); fee VAT = 1/6 of the VAT-bearing columns (not affiliate / seller-funded promotion). "Shipping" (TikTok label) = actual shipping cost. Preview checks Net sales + Fees + Shipping against "Total settlement amount". Tested 2026-10-06 (LW-3).
- **Mirakl:** Excel (.xlsx) settlement export, multi-row per order line; group by "Order line ID". Rows used: Order amount, Shipping charges and their tax rows, plus every fee type (any non-refund type containing "commission" or "fee"; "tax" in the type = its VAT), e.g. The Range's "Seller fee on order" (MARK_FEE 2%, PAY_GATE_FEE 1%). Fees with no Order line ID are order-level: shared across that Order number's lines by gross sale price (last line takes the leftover penny). Unknown types are listed in the status. Some retailers (B&Q) have "Order amount tax" / "Shipping tax" rows with Order amount net; others (Debenhams) have none and Order amount is gross, so when a line has no tax row the importer passes `null` and the VAT comes from the product's `vat_rate`. Refunds are skipped for now. Retailer picker lists platforms where `integration_type = 'mirakl'`.
- **OnBuy:** transaction report (.xlsx or CSV), one row per order line; `externalId` = Order Number. Revenue = "Items £" (+ "Delivery £" as shipping revenue), fees = "Total Fees Inc. TAX £" (sales fee + Boost fee) with VAT = "Fees TAX". **Boost is OnBuy advertising**, chosen per SKU: "Boost Fee %" (e.g. 20%), "Boost Fee Per Item £" = net ad cost, "Boost Fee TAX Per Item £" = its VAT, "Total Boost Fee" = the net ad deduction. Currently counted inside fees; belongs in the Advertising layer (roadmap). Sale VAT isn't in the file for UK sellers ("Deemed Supplier TAX" empty), so the importer passes `saleVatPence: null` and `importEngine` works it out from the product's `vat_rate`. Rows without SKU / positive Items £ (refunds) are skipped. Preview checks each row against "Net Proceeds".
- **Shopify:** orders export (CSV) + optional Shopify Payments transactions export. Orders file has one row per product, but order-level columns (Financial Status, Created at, Shipping, Discount Amount, Total, Cancelled at, Payment Method) are only on each order's first row; group by "Name" (also `externalId`). Imports `paid` / `partially_refunded`, skips cancelled/refunded/voided/unpaid. Line gross = Lineitem price × qty − Lineitem discount; any leftover order Discount Amount, the Shipping charged and the order's fee are shared across lines by gross (last line takes the leftover penny). Fees = "charge" rows' Fee (+ VAT column, 0 for UK) matched on "Order". Sale/shipping VAT = `null` (from product rates). Preview checks lines + shipping against Shopify's Total (assumes VAT-inclusive prices). PayPal fees aren't in either file: PayPal orders count £0 fees for now (payment fee settings on the roadmap).
- **eBay:** transaction report (CSV or .xlsx) from Seller Hub → Payments → Reports. Notes block above the table: read with `readSpreadsheet(file, dates, { headerStartsWith: 'Transaction creation date' })`. One "Order" row per item sold; `externalId` = Transaction ID (Order number kept for grouping). SKU = **Custom label** (required: Item ID is shared by all variations, so rows without a Custom label are held back and listed by Item ID). Revenue = "Item subtotal" (gross) + "Postage and packaging" as shipping revenue; sale VAT `null` (from product rate). Fees = every column with "fee" in its name, negative, inc. 20% VAT (1/6); "Final value fee – variable" = commission, the rest other_fee; the dash in "Final value fee – fixed" arrives garbled, so columns are matched by pattern. Dates like "31-Jul-26". Preview checks subtotal + postage − fees against "Net amount". Not yet: refunds, postage labels (actual shipping), Promoted Listings ("Other fee" rows, belongs in advertising), multi-item orders untested.
- **Temu:** transaction export (CSV or .xlsx), one "Order Payment" row per order item; `externalId` = "Order item ID". "SKU" is the product title; "SKU ID" (Temu's number) → seller SKU via `channel_sku_ids`. "Retail price" is ex. VAT and "Product Tax" its VAT (Temu pays it over to the seller), so sale gross = Retail price − Seller discount + Product Tax, `saleVatPence` = Product Tax. Shipping + Shipping Tax = shipping revenue. Fees = "Service fee (tax incl.)", 20% VAT inside (1/6), commission. Preview checks against "Total". Platform discount / Platform incentive (+ shipping, tax) / Others aren't used yet: rows with them are flagged. Refunds and other types skipped.
